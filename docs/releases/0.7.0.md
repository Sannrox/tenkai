# Release notes: v0.7.0

Crate version: **`0.7.0`**. Tag: **`v0.7.0`**. Release candidate:
`v0.7.0-rc.1` (pre-release), verified with the bare-host drill on its
published binaries.

Pair with [release readiness](../release-readiness.md). Contributor credits
belong on the GitHub Release generated notes.

## Scope

Pre-1.0 minor release on published GitHub release
[v0.6.0](https://github.com/Sannrox/tenkai/releases/tag/v0.6.0). Theme: one
Tenkai on a bare host. An operator installs only Tenkai; Tenkai installs a
single-node cluster as a privileged host release and delivers releases into
that cluster from one control plane, with the server never running as root
([ADR 0041](../decisions/0041-per-release-executor-and-privileged-host-releases.md),
[bare host guide](../bare-host.md)).

It also carries the trust fixes that path depends on: signer windows checked
at an artifact's signed time, hardened stored grant rules, and the signed
format breaks taken together before 1.0. Runner attestations, derived
criticality, recall notices and topology drills now sign the bytes sent;
outcome and tenant-mode feedback export move to new schema ids with
unambiguous tenant targets.

Base: tag `v0.6.0`. Changes: `v0.6.0..v0.7.0`, through #980.

Gate flags: `breaking`, `migration`.

### Operator upgrade notes

1. **Embedded / SQLite:** install `0.7.0` hosts from the GitHub Release after
   verifying `SHA256SUMS` and the attestation, or with the attached
   `install.sh` (#928). The schema stays 13, so a 0.6.0 store opens without
   migration. A store from an older schema gets a verified copy
   `<db>.pre-v<found>.<ms>.<id>.db` first, which needs free space about the
   size of the store; the start is refused if the copy cannot be written
   (#927). Rolling back uses the newest copy
   ([operational storage](../operational-storage.md)).
2. **Outcome export (#944):** only hosts with outcome export enabled.
   Register `tenkai.terminal_outcome.v2@2.0.0` from
   `api/tenkai-terminal-outcome-v2.schema.json` at the release tag and keep
   `.v1`. On a tenant-mode hub, also add target kind
   `tenkai.tenant_deployment` and keep `tenkai.deployment`. Then upgrade with
   `TENKAI_OUTCOME_PROVIDER_REGISTRATION` naming the `.v2` schema (and the
   tenant target kind on a tenant-mode hub). A host that still attests `.v1`
   refuses to start. See
   [provider contracts](../provider-contracts.md#upgrading-from-v1-070).
3. **Tenant-mode feedback export (#959):** only tenant-mode hubs with
   feedback export enabled. Add target kind `tenant_feedback_observation` and
   keep `feedback_observation`, then upgrade with
   `TENKAI_FEEDBACK_PROVIDER_REGISTRATION` changed to
   `target_kind=tenant_feedback_observation`. Community hosts keep their
   registration. See
   [provider contracts](../provider-contracts.md#upgrading-tenant-mode-feedback-export-070).
4. **Mixed versions for export:** rows queued before the upgrade deliver
   with their old envelope and target. Older replicas still running during a
   rolling upgrade, or after a rollback, refuse `.v2` rows as a visible,
   retryable failure until a 0.7.0 replica delivers them. Remove the old
   registrations only after no older replica runs and nothing queued before
   the upgrade is undelivered.
5. **Feedback capture and delivery (#954, #946):** tenant-mode PostgreSQL
   hubs now write `tenkai.feedback_observation.v1` records; history starts at
   the upgrade. A denied or parked observation stays in the outbox with its
   reason and retries instead of being marked delivered.
6. **Signed statements (#929, #933, #951):** upgrade every server and
   `tenkaictl` that imports derived criticality, recall notices, or drill
   evidence before switching producers or external signers to `.v2`.
   Releases before 0.7.0 refuse `.v2` as malformed. Runner agents and
   servers upgrade in either order; 0.7.0 servers still accept 0.6.x agents'
   `.v1` attestations, and #940 tracks removing that in a later release.
   `tenkaictl bundle build` refuses `.v1` derived criticality; re-sign first.
   Imported recall notices keep their stored form and object id.
7. **Signer windows (#925, ADR 0042):** stored artifacts are checked at
   their signed time, so setting `not_after` on a rotated key no longer
   breaks what it already signed. Live admissions (plan and migration
   approvals, exporter key at bundle build, derived criticality) still check
   at now. The per-class table is in [release signing](../release-signing.md).
8. **Per-release executor (#922, #938):** declare `[deploy] executor` only
   after every server and runtime that reads the catalog runs 0.7.0. A
   declared executor the process lacks fails the step before anything
   changes. A plan that moves a product to another executor in place is
   refused; remove, then install. On a server that sets
   `TENKAI_SOFTWARE_EXECUTOR`, apply through the management API now uses that
   executor for undeclared releases, matching the reconciler. Kubernetes
   releases no longer need a placeholder `deploy.install`.
9. **Host releases (#937, #941, #948, #965, #970, #973, #975):** hosts that do
   not use `executor = "host"` need no change. To use host releases, install
   the applier with `install.sh --role server --with-host-applier` (root),
   which places `tenkai-host-applier`, the `tenkai-host-apply@.service`
   template and the polkit rule, then add the root-owned trust roots and host
   approval policy in `/etc/tenkai`, and set `TENKAI_HOST_SPOOL_DIR` (and
   `TENKAI_HOST_STATE_DIR` when it is not `/var/lib/tenkai-host`) on the
   server ([host releases](../host-releases.md),
   [run tenkai-server](../run-tenkai-server.md)). Host steps are never
   auto-approved: approve them with keys from the host approval policy that
   the `tenkai` user cannot read. A failed host step stays failed; rollback is
   an approved plan. Remove a host product with `tenkaictl env unsubscribe`
   and an approved plan. Catalog recall is not visible to the root side;
   approval expiry bounds that window.
10. **In-cluster releases before the cluster exists (#972):**
    `env cluster-config set` accepts a path whose file does not exist yet. An
    in-cluster release whose cluster config is missing is refused before it
    changes anything and converges through reconcile backoff once the file
    appears.
11. **Stored grant rules (#924, #936, #952):** a stored rule only adds to
    what the grant file grants a principal. An unreadable or invalid row is
    withheld and reported (`stored_grant_rules_withheld` on `/healthz`), and
    tokens matching a withheld claim value that the grant file does not grant
    are refused. A committed create or remove always answers success. A write
    whose outcome is unknown is audited `grant_rule.*.failed` (it was
    `refused`) and makes that replica not ready until a later read succeeds;
    alerts on `grant_rule.*.refused` should also match `*.failed`. A retry
    against a moved generation that already landed answers `409`. Earlier
    releases still drop all stored rules on one unreadable row, so do not
    write a later rule format until every replica runs 0.7.0.
12. **Hub PostgreSQL (#942):** the first use of each tenant schema rebuilds
    the property lookup index on a 256-character value prefix, so plans of
    about 25 or more steps store. Writes to that tenant's catalog properties
    wait for the rebuild. Rolling deploys and rollback stay correct.
13. **Linux hosts (#921):** built at a glibc 2.28 floor and checked against
    it: RHEL 8 and 9, Debian 10+, Ubuntu 20.04+, Amazon Linux 2023. Musl is
    not supported, and `install.sh` refuses it.

### Rollback

Previous `0.6.0` binary. The SQLite schema is unchanged, so a 0.7.0 store
opens on 0.6.0 without a restore. Before rolling back:

- on a host with outcome export, set `TENKAI_OUTCOME_PROVIDER_REGISTRATION`
  back to its 0.6.0 value (`.v1@1.0.0`, and `target_kind=tenkai.deployment`
  on a tenant-mode hub); on a tenant-mode hub with feedback export, set
  `TENKAI_FEEDBACK_PROVIDER_REGISTRATION` back to
  `target_kind=feedback_observation`. 0.6.0 requires its exact registration
  string and refuses to start with the 0.7.0 values. Keep both
  registrations in the evidence store;
- outcome and feedback rows enqueued as `.v2` stay retrying on 0.6.0 and
  deliver once a 0.7.0 replica runs again; keep both registrations until
  then;
- 0.6.0 refuses `.v2` derived-criticality envelopes, recall notices, and
  drill evidence, any manifest that declares `[deploy] executor`, and plans
  with host or `remove` steps;
- a PostgreSQL tenant schema keeps the rebuilt index, which 0.6.0 reads
  correctly.

## User-visible changes

### Added

- Bare host to cluster to in-cluster release with one Tenkai, with a
  reference cluster host release, a guide and a CI drill (#979)
- Privileged host releases: the root-side `tenkai-host-applier` with a
  systemd template unit and polkit rule (#937, #941, #948), driven by the
  server's host executor (#970), with uninstall through an approved plan and
  `tenkaictl env unsubscribe` (#973)
- `tenkai-host-applier` and its unit and rule ship with the Linux hosts
  (#965)
- Optional signed `[deploy] executor` per release, resolved per operation
  (#922, #938)
- Verified pre-migration copy of the SQLite store (#927)
- `install.sh` on each Release for CLI, server, and runtime hosts (#928)
- Signed `vX.Y.Z-rc.N` tags publish GitHub pre-releases (#923)

### Changed

- Terminal outcomes move to `tenkai.terminal_outcome.v2` with tenant-scoped
  targets (#944)
- Tenant-mode feedback export moves to `tenkai.feedback_export.v2` (#959)
- Runner attestations, derived criticality, recall notices, and topology
  drills sign the bytes sent under `.v2` schemas (#929, #933, #951)
- Linux hosts build at a glibc 2.28 floor (#921)
- `tenkaictl init` prints the schema type count instead of every name (#964)
- The README is a five-minute front door (#961)

### Fixed

- Signer windows are checked at an artifact's signed time (#925)
- Tenant-mode PostgreSQL hubs capture feedback observations (#954)
- A feedback observation is marked delivered only when admitted (#946)
- Stored grant rules cannot narrow or lock out a file principal (#924), are
  read one row at a time (#936), and a committed change reports done (#952)
- Large plans store on PostgreSQL hubs (#942)
- An unavailable executor target leaves the deployment as it was (#972)
- The host applier keeps `CAP_SETUID`, so host commands can switch user
  (#975)
- A just-released file lock is settled before refusing as held (#955)
- The Linux host build no longer fails on SIGPIPE from `ldd` (#930)
- Test flakes fixed at the root (#939, #950, #957, #966)

### Security

- Signed statements verify over received bytes before parsing (#929, #933,
  #951)
- Host releases run as root only through a verified, sandboxed, once-only
  applier path; the server never runs as root (#937, #941, #948, #970)
- Stored grant rules fail closed when a write's outcome is unknown (#952)

### Migration

- GATE:mig. PostgreSQL tenant schemas rebuild one index on first use (#942).
  SQLite `SCHEMA_VERSION` stays 13. HTTP contract id stays `tenkai.http.v1`.

## Out of scope for 0.7.0

- Removing deprecated `.v1` signed statements (#940)
- `.deb`/`.rpm`, a package tap, `linux-aarch64` hosts, a macOS launchd target
  (#917)
- Remote publish of releases with deploy inputs (#976)
- Spoke-standby evidence signed over the bytes sent (#953)
- Runway listing of stored artifacts (#920)
- Releasing the console. It has no changes since `v0.2.0`
