# Release notes: v0.7.0

Crate version: **`0.7.0`**. Tag: **`v0.7.0`**.

Pair with [release readiness](../release-readiness.md). Contributor credits
belong on the GitHub Release generated notes.

## Scope

Pre-1.0 minor release on published GitHub release
[v0.6.0](https://github.com/Sannrox/tenkai/releases/tag/v0.6.0). Moves
outcome and tenant-mode feedback export to new schema ids with unambiguous
tenant targets, signs runner attestations, derived criticality, recall
notices and topology drills over the bytes sent, checks signer windows at an
artifact's signed time, and lets a release name its software executor. Also
takes a verified copy of a SQLite store before it migrates, hardens stored
grant rules, builds Linux hosts at a glibc 2.28 floor, and attaches a
one-command `install.sh` to each Release.

Base: tag `v0.6.0`. Changes: `v0.6.0..v0.7.0`, through #959.

Gate flags: `breaking`, `migration`.

## Compatibility and migration

| Surface | Impact for 0.7.0 |
| --- | --- |
| Crate version | `0.6.0` → `0.7.0` for `tenkai` and every workspace crate, including the new `tenkai-host-applier` |
| SQLite `SCHEMA_VERSION` | Unchanged at 13. A start that migrates an older store first writes a verified copy beside it (#927) |
| Hub PostgreSQL | One-time rebuild of `catalog_object_properties_lookup` per tenant schema on first use (#942). GATE:mig |
| HTTP contract | Id stays `tenkai.http.v1`. Grant-rule listing gains `applied`, `not_applied_reason`, `unreadable`. Derived-criticality import takes the v2 envelope |
| Runtime protocol | `428 attestation_missing` gains `accepted_schemas`; new `403 attestation_schema_unsupported` (#929) |
| Provider export | `tenkai.terminal_outcome.v2@2.0.0` (#944) and `tenkai.feedback_export.v2` (#959). Registrations must change before upgrade on affected hosts |
| Signed statements | `.v2` for runner attestation, derived criticality, recall notice, topology drill. `.v1` still verified, never produced |
| Manifest | Optional `[deploy] executor` (#922). Older hosts refuse a manifest that declares it |
| Contract constants | `AUTH_CONTEXT`, `RUNTIME_CAPABILITY`, `FEDERATED_IDENTITY`, `PROVIDER`, `MODEL_RUNTIME` contract versions and `PLAN_FORMAT_VERSION` unchanged |
| Rust library API | Breaking: `ExecutionOptions.software_executors`, `DeploySection.executor`, `plan::Step.host`, grant-rule store types, runner attestation signing |
| Web console | `ui/console.pin` unchanged (`v0.2.0`) |
| GitHub Release assets | Same host names as 0.6.0, plus `install.sh`. `tenkai-host-applier` is not attached (#949) |
| Linux hosts | glibc 2.28+ on x86-64 (#921) |
| Toolchain | `rust-version = "1.96.1"` |
| Defaults | Signing/approval fail closed; tenant mode / enterprise flags default off for community SQLite |

### Operator upgrade notes

1. **Embedded / SQLite:** install `0.7.0` hosts from the GitHub Release after
   verifying `SHA256SUMS` and the attestation, or with the attached
   `install.sh` (#928). The schema stays 13, so a 0.6.0 store opens without
   migration. A store from an older schema gets a verified copy
   `<db>.pre-v<found>.<ms>.<id>.db` first; the start is refused if the copy
   cannot be written (#927). `tenkaictl --version` reports `tenkaictl 0.7.0`.
2. **Outcome export (#944):** only hosts with `--outcome-provider chisei`.
   Register `tenkai.terminal_outcome.v2@2.0.0` from
   `api/tenkai-terminal-outcome-v2.schema.json` at the release tag and keep
   `.v1`. On a tenant-mode hub, also add target kind
   `tenkai.tenant_deployment` and keep `tenkai.deployment`. Then upgrade with
   `TENKAI_OUTCOME_PROVIDER_REGISTRATION` naming the `.v2` schema (and the
   tenant target kind on a tenant-mode hub). A host that still attests `.v1`
   refuses to start. See
   [provider contracts](../provider-contracts.md#upgrading-from-v1-070).
3. **Tenant-mode feedback export (#959):** only tenant-mode hubs with
   `--feedback-provider chisei`. Add target kind
   `tenant_feedback_observation` and keep `feedback_observation`, then
   upgrade with `TENKAI_FEEDBACK_PROVIDER_REGISTRATION` changed to
   `target_kind=tenant_feedback_observation`. Community hosts keep their
   registration. See
   [provider contracts](../provider-contracts.md#upgrading-tenant-mode-feedback-export-070).
4. **Mixed versions for export:** rows queued before the upgrade deliver
   with their old envelope and target. Older replicas still running during a
   rolling upgrade, or after a rollback, refuse `.v2` rows as a visible,
   retryable failure until a 0.7.0 replica delivers them. Remove the old
   registrations only after no older replica runs and nothing queued before
   the upgrade is undelivered.
5. **Feedback capture (#954):** tenant-mode PostgreSQL hubs now write
   `tenkai.feedback_observation.v1` records. History starts at the upgrade.
6. **Signed statements (#929, #933, #951):** upgrade every server and
   `tenkaictl` that imports derived criticality, recall notices, or drill
   evidence before switching producers or external signers to `.v2`.
   Releases before 0.7.0 refuse `.v2` as malformed. Runner agents and
   servers upgrade in either order; 0.7.0 servers still accept 0.6.x agents'
   `.v1` attestations, and #940 tracks removing that in a later release.
   `tenkaictl bundle build --derived-criticality` refuses `.v1`; re-sign
   first.
7. **Signer windows (#925, ADR 0042):** stored artifacts are checked at
   their signed time, so setting `not_after` on a rotated key no longer
   breaks what it already signed. Live admissions (plan and migration
   approvals, exporter key at bundle build, derived criticality) still check
   at now. The per-class table is in [release signing](../release-signing.md).
8. **Per-release executor (#922, #938):** declare `[deploy] executor` only
   after every server and runtime that reads the catalog runs 0.7.0. A
   declared executor the process lacks fails the step before anything
   changes. A plan that moves a product to another executor in place is
   refused; remove, then install. On a server that sets
   `TENKAI_SOFTWARE_EXECUTOR`, apply through the management API now uses that
   executor for undeclared releases, matching the reconciler.
9. **Host releases are not usable yet:** `executor = "host"` parses and is
   signed, and `tenkai-host-applier` builds from source with a reference
   systemd unit and polkit rule ([host releases](../host-releases.md)). The
   server side (#911) and the Release asset (#949) are not in 0.7.0, so a
   host step always fails with "the host executor is not available in this
   process". Do not publish host releases to 0.7.0 environments.
10. **Stored grant rules (#924, #936, #952):** a stored rule only adds to
    what the grant file grants a principal. An unreadable or invalid row is
    withheld and reported (`stored_grant_rules_withheld` on `/healthz`). A
    write whose outcome is unknown answers `503`, is audited
    `grant_rule.*.failed`, and makes that replica not ready until a later
    read succeeds. A retry against a moved generation that already landed
    answers `409`. Earlier releases still drop all stored rules on one
    unreadable row, so do not write a later rule format until every replica
    runs 0.7.0.
11. **Hub PostgreSQL (#942):** the first use of each tenant schema rebuilds
    the property lookup index on a 256-character value prefix, so plans of
    about 25 or more steps store. Writes to that tenant's catalog properties
    wait for the rebuild. Rolling deploys and rollback stay correct.
12. **Linux hosts (#921):** built at a glibc 2.28 floor and checked against
    it: RHEL 8 and 9, Debian 10+, Ubuntu 20.04+, Amazon Linux 2023.
    Musl is not supported.

### Rollback

Previous `0.6.0` binary. The SQLite schema is unchanged, so a 0.7.0 store
opens on 0.6.0 without a restore. Before rolling back:

- outcome and feedback rows enqueued as `.v2` stay retrying on 0.6.0 and
  deliver once a 0.7.0 replica runs again; keep both registrations until
  then;
- 0.6.0 refuses `.v2` derived-criticality envelopes, recall notices, and
  drill evidence, and any manifest that declares `[deploy] executor`;
- a PostgreSQL tenant schema keeps the rebuilt index, which 0.6.0 reads
  correctly.

## User-visible changes

### Added

- Optional signed `[deploy] executor` per release, resolved per operation
  (#922, #938)
- Verified pre-migration copy of the SQLite store (#927)
- `install.sh` on each Release for CLI, server, and runtime hosts (#928)
- Signed `vX.Y.Z-rc.N` tags publish GitHub pre-releases (#923)
- Release workflow verifies the signed tag, writes an SBOM and the family
  release manifest, and takes notes from this changelog (#897)
- Root-side `tenkai-host-applier` with request verification, durable
  applied state, systemd unit, and polkit rule, built from source (#937,
  #941, #948)
- ADR 0041: per-release executor and privileged host releases (#908)

### Changed

- Terminal outcomes move to `tenkai.terminal_outcome.v2` with tenant-scoped
  targets (#944)
- Tenant-mode feedback export moves to `tenkai.feedback_export.v2` (#959)
- Runner attestations, derived criticality, recall notices, and topology
  drills sign the bytes sent under `.v2` schemas (#929, #933, #951)
- Linux hosts build at a glibc 2.28 floor (#921)

### Fixed

- Signer windows are checked at an artifact's signed time (#925)
- Tenant-mode PostgreSQL hubs capture feedback observations (#954)
- A feedback observation is marked delivered only when admitted (#946)
- Stored grant rules cannot narrow or lock out a file principal (#924), are
  read one row at a time (#936), and a committed change reports done (#952)
- Large plans store on PostgreSQL hubs (#942)
- A just-released catalog file lock is settled before refusing as held
  (#955)
- The Linux host build no longer fails on SIGPIPE from `ldd` (#930)

### Security

- Signed statements verify over received bytes before parsing (#929, #933,
  #951)
- Stored grant rules fail closed when a write's outcome is unknown (#952)

### Migration

- GATE:mig. PostgreSQL tenant schemas rebuild one index on first use (#942).
  SQLite `SCHEMA_VERSION` stays 13. HTTP contract id stays `tenkai.http.v1`.

## Out of scope for 0.7.0

- Cutting `v0.7.0` (maintainer)
- Server-side host executor (#911) and shipping `tenkai-host-applier` (#949)
- Removing deprecated `.v1` signed statements (#940)
- Release from main for a signed tag (#915, #916)
- `.deb`/`.rpm`, a package tap, `linux-aarch64` hosts (#917)
- Releasing the console. It has no changes since `v0.2.0`
