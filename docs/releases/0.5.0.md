# Release notes: v0.5.0

Crate version: **`0.5.0`**. Tag: **`v0.5.0`**.

Pair with [release readiness](../release-readiness.md). Contributor credits
belong on the GitHub Release generated notes.

## Scope

Pre-1.0 minor release on published GitHub release
[v0.4.2](https://github.com/Sannrox/tenkai/releases/tag/v0.4.2). Adds a Docker
host executor for multi-container releases, policy-driven automatic approval,
signed CI publishing, signed compatibility profiles, and delivery approval
gates and holds. Hardens automatic approval and failed-target handling.

Base: tag `v0.4.2` (`2a45975`). Changes: `v0.4.2..` through #593.

### Operator upgrade notes

1. **Embedded / SQLite:** install `0.5.0` hosts from the GitHub Release after
   verifying `SHA256SUMS` and the attestation. No store migration.
   `tenkaictl --version` reports `tenkaictl 0.5.0`. See
   [release binaries](../release-binaries.md).
2. **Release trust (#577):** configure the release trust file on every host
   that accepts remote publication or deploys beyond the local host, via
   `TENKAI_RELEASE_TRUST_ROOTS`. Trust roots supplied by a caller are ignored,
   so publication and deployment fail closed until the host file is in place.
3. **Remote apply status (#580):** a remote apply whose delivery steps fail
   now returns HTTP `422` and `tenkaictl` reports the failure. A `0.5.0`
   `tenkaictl` talking to an older server still reports such an apply as
   succeeded, so upgrade servers before relying on the result.
4. **Failed releases are held (#579):** automatic convergence no longer
   re-plans a release that failed. To retry, create, approve, and apply an
   explicit plan; `status` reports the hold.
5. **Automatic approval (#587, #591, #592):** automatic signers act only
   within the environment's current policy, and downgrades always need human
   signatures. Automation that relied on auto-approving downgrades now stops
   at approval. Changing or clearing the policy revokes earlier automatic
   approvals; the reconciler renews the ones the new policy still allows.
6. **Executor guard (#559):** hosts resolve `tenkai-executor-guard` from
   `TENKAI_EXECUTOR_GUARD`, then beside the host binary, then one directory
   up. A configured path that is not an executable file is rejected. Pass
   `--require-executor` to `tenkai-server` to refuse startup when the shell
   executor is unavailable; without it, startup continues. The guard ships in
   the release assets.
7. **CI publishing (#557):** publishing needs the new, narrower `publish`
   delivery capability (`management` also satisfies it). For non-interactive
   sign-in, the OIDC client secret is read only from
   `TENKAI_OIDC_CLIENT_SECRET` in the environment.
8. **Docker executor (#529):** new in this release, so upgrading from `0.4.2`
   recreates no containers. Containers carry a `tenkai.spec-digest` label
   covering the container spec, the resolved `env_file` path and contents,
   and configuration files. A container is recreated whenever that digest,
   its image, version, release, or config digest changes. Containers created
   by builds from before this release with an older spec digest are
   recreated once on the first apply.

### Rollback

Previous `0.4.2` binary plus the existing Tenkai-owned store. No schema
change. Docker deployments need the Docker executor, which `0.4.2` does not
include.

## User-visible changes

### Added

- Docker host executor for multi-container releases (#529), with host
  networking and registry image digest admission (#570), completion-gated
  initialization jobs (#572), release-owned configuration files (#573), and
  runtime user, mounts, and restart policy (#575)
- Automatic plan approval from an environment policy (#556)
- `tenkaictl` publishes signed, digest-pinned releases from CI with
  non-interactive authentication (#557)
- Signed software compatibility profiles enforced before deployment (#571)
- Migration and identity-change metadata that requires human approval, plus
  environment and channel delivery holds (#578)
- `tenkaictl` sign-in with OIDC PKCE (#527)
- Versioned `json-v1` command results in remote mode (#580)
- `tenkai-server` resolves `tenkai-executor-guard` at startup (#559)

### Changed

- Docker images are pulled before replace, and matching containers are
  skipped (#555)
- Publish capability is advertised in contract routes (#576)

### Fixed

- Remote publication trust roots are pinned on the server (#577)
- Automatic signers are confined to their environment's policy (#587)
- Downgrades require human signatures (#591)
- Stale automatic approvals are refreshed (#592)
- Failed targets stay held until a deliberate retry (#579, tests #593)
- Graceful shutdown on SIGTERM as well as SIGINT (#558)
- Docker: reject volume paths that inject `--mount` fields (#542), list
  container names during cleanup (#548), hash runtime names so hyphenated
  scopes cannot collide (#554), restore previous containers when an upgrade
  fails (#568), recreate containers when their `env_file` changes (#569)
- Token cache refresh is serialized across processes (#543)

### Migration

- None. `SCHEMA_VERSION` remains 12. HTTP contract id stays `tenkai.http.v1`.

## Out of scope for 0.5.0

- Extra platforms or crates.io
- Rewriting `docs/releases/0.4.2.md`
