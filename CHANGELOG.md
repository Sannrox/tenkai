## v0.8.0 (2026-11-11)

Gate flags: breaking, migration

Products run as named instances that depend on
each other through declared contracts (ADR 0043, ADR 0044). The environment
runtime runs the built-in executors, delivers sealed secrets (ADR 0045), and
issues and rotates workload certificates with peer grants from dependency
bindings (ADR 0046). Operators sign in through host identity on a Unix socket
(ADR 0047), unsubscribed instances are removed by an approved plan

### Upgrade
- Web console: `ui/console.pin` moves from `v0.2.0` to `v0.3.1`. The console reads the new instance, drift, history, identity and apply-step fields when the server returns them, and still requires `tenkai.http.v1` on `/healthz`.
- Install 0.8.0 hosts from the GitHub Release after verifying `SHA256SUMS` and the attestation, or with `install.sh`. `tenkaictl --version` reports `tenkaictl 0.8.0`. Upgrade every server, runtime and host applier before using any new manifest, step or secret feature below; older binaries refuse those shapes and fail closed.
- Store migration (#1044): the SQLite operational store moves from schema 13 to 14, keyed by instance. The first 0.8.0 start writes a verified pre-migration copy beside the store, or refuses to start. Older binaries refuse the migrated store. Postgres hubs run additive tenant DDL (stamp 3, #1099) once per tenant schema.
- Instances (#1044, #1045): existing records stay the default instance of their product. `env subscribe --instance` and HTTP `instance` are optional and default to the product. Unlabeled pre-upgrade objects belong to the default instance.
- Unsubscribe (#1153): `env unsubscribe` needs `--version` (`expected_version`) while a release is recorded for the instance, and the next approved plan removes a non-host instance. Helm removals need Helm 3.13 or later.
- Manifests: declare `[deploy.identity]` (#1159) or `[config]` (#1113) only after every server and runtime runs 0.8.0. Older servers refuse them.
- Sealed secrets (#1099, #1103, #1116, #1131, #1148): set `TENKAI_RUNTIME_APPROVAL_POLICY` on each runtime before the first `tenkaictl secret set`, and set the first sealed value only after every server is upgraded. Host targets need the applier spool on tmpfs and swap off or encrypted.
- Workload identity (#1155, #1159, #1164, #1168 to #1171): the server sends issuer, rotation and peer-grant plans only to runtimes that advertise the matching capability; older runtimes stay idle on them. After upgrade the first plan re-renders certificate holders once. Until it runs, rollbacks and restarts of a caller of a certified provider are refused.
- Host identity (#1035): install writes `host-grants.toml`, creates the `tenkai-viewer`, `tenkai-operator` and `tenkai-admin` groups and the `/run/tenkai` socket directory. TCP still requires a bearer or assertion.
- Spoke standby (#1156): `tenkaictl spoke-standby promote` takes `--environment`, `--state` is the restored SQLite store, and every member passes the same `--lease-dir`. `spoke-standby.json` is no longer read.
- Reconcile fence (#1157): replicas no longer use `tenkai_reconcile_tick_claims`. Drop the table once every replica runs 0.8.0.
- Feedback (#1104 to #1106): `TENKAI_FEEDBACK_PROVIDER_REGISTRATION` must attest `evidence_type=tenkai.feedback_observation;schema=tenkai.feedback_observation.v1@1.0.0`. Keep `feedback.observation@1.0.0` on the plane until no older replica remains.
- HTTP clients (#1175): operation results accept unknown fields. A client from before 0.8.0 still refuses a result field it does not know.
- Rust API: every `!` change above alters public library types or signatures; see each pull request's Breaking section. Wire formats stay additive unless noted.
- Rollback to 0.7.1: stop the server, restore the pre-migration copy of the store, and start 0.7.1. Changes made after the upgrade are lost. Runtimes and appliers roll back with their server.

## v0.7.1 (2026-11-06)

Gate flags: none

Patch on 0.7.0: `kubernetes-inprocess` waits renew the apply lease, wait for
the applied revision, and keep diagnosed causes if the lease is lost.
Unknown `TENKAI_SOFTWARE_EXECUTOR` refuses at start. Full operator notes:
[docs/releases/0.7.1.md](https://github.com/Sannrox/tenkai/blob/v0.7.1/docs/releases/0.7.1.md).

### What's Changed
- fix(executor): keep diagnosed causes when an in-process wait loses the apply lease (#999)
- fix(executor): refuse unknown TENKAI_SOFTWARE_EXECUTOR instead of falling back to shell (#998)
- fix(executor): wait for the applied kubernetes revision, not merely Available (#996)
- fix(executor): renew the apply lease during in-process waits and name the workload failure cause (#986)
- fix(examples): keep the service load balancer and local-path storage in the reference cluster (#984)

### Upgrade
- Install 0.7.1 hosts from the GitHub Release after verifying `SHA256SUMS` and the attestation, or with `install.sh`. The SQLite schema stays 13; no store migration. `tenkaictl --version` reports `tenkaictl 0.7.1`.
- kubernetes-inprocess (#986, #996, #999): a wait longer than the apply lease TTL keeps the lease. An upgrade waits until the applied revision is the one serving, not merely `Available` on leftover pods. If the lease is still lost, the error names the last workload causes first. Diagnosis of ReplicaSets and pods needs `list` in the environment namespace; without it the wait continues on conditions and names the read error.
- `TENKAI_SOFTWARE_EXECUTOR` (#998): an unknown or uninstalled value refuses `tenkai-server` and embedded hosts at start instead of running undeclared releases as shell. Unset (or `shell`) remains the process default. `/readyz` advertises `software_executor:<kind>` for the default that actually runs.
- Reference cluster example (#984): the bundled k3s unit keeps the service load balancer and local-path storage. An operator who already installed that product publishes a newer version and applies it as an upgrade.
- Rollback to 0.7.0: the previous binary plus the existing store. No schema change. 0.7.0 ignores `failed_target_error.<product>` and still treats an unknown `TENKAI_SOFTWARE_EXECUTOR` as shell. A 0.7.0 host can report an in-process upgrade complete while old pods keep the Deployment Available.

- Feedback capture on tenant-mode PostgreSQL hubs (#868): committed deployment outcomes write no `tenkai.feedback_observation.v1` record on these hubs, with no error. SQLite hubs capture them. Do not rely on observation history from a tenant-mode PostgreSQL hub.

4. **Optional provider hosts:** vendored Sekai/Chisei contracts moved to the
   1.0 façade (#211, #213). Pin a compatible sekai-chisei revision.
   Tenkai remains recoverable without the provider unless policy requires
   its evidence.
5. **Optional multi-tenant hub:** enable `postgres`, set

   [postgres-tenant-store.md](https://github.com/Sannrox/tenkai/blob/v0.3.0/docs/postgres-tenant-store.md). Do not
   co-locate IdP databases.
6. **Multi-replica hubs:** follow
   [multi-replica-hub-runbook.md](https://github.com/Sannrox/tenkai/blob/v0.3.0/docs/multi-replica-hub-runbook.md). Prefer
   one active writer plus a shared durable fence; do not share community
   SQLite files.

#### Rollback

Previous binary plus restore of the pre-upgrade Tenkai-owned SQLite backup
(embedded) or Postgres `pg_restore` (hub), then re-inject tokens from the
secret store. Recovery never depends on sekai-chisei.
